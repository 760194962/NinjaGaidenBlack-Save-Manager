# system.dat 研究：读档列表的游玩时间与顺序

TitleID 5443000D（忍者外传 黑之章，Xbox）。`TDATA\5443000d\system.dat` 里存着读档列表用的**每档游玩时间**和**显示顺序**。
签名/加密方式见 [save-format-research.md](save-format-research.md)，本文只讲 system.dat 的内容和游戏对它的读写逻辑。
工具实现：[`ngb_system_dat.py`](../ngb_system_dat.py)（GUI 里的"system.dat 更新…"调用同一套代码）。

## 1. 要点
- 读档列表显示的时间来自 system.dat 里的"每档帧数表"，**不是** save000.dat。
- 读档时游戏取 `max(存档里的帧数, 表里该档的值)`。表里的值更大，读档后时间会跳到表里的值。
- 列表的显示顺序存在 system.dat 的"顺序表"里（见 §4）。

## 2. 文件与加密
固定 0x550（1,360）字节：

| 偏移 | 内容 |
|---|---|
| 0x00–0x13 | HMAC 签名，与 save000.dat 相同的非漫游签名（`sign_raw`） |
| 0x14–0x17 | seed（u32 小端） |
| 0x18– | 0x538 字节，加密方式与 save000.dat 相同（`decrypt_save`） |

加密是解密的逆过程：先每 8 字节做 Blowfish enc，再与 MT 输出逐个 u32 异或，使用同一个 seed 和同一把 56 字节 key（`encrypt_save`）。`encrypt(decrypt(x)) == x` 已验证。

## 3. 解密后：区间编码流
解密后的 0x538 字节是一段 Subbotin carryless range coder 压缩流 + 游戏缓冲区里的残留：

- byte0 = 频率表格式：`0x00` 不压缩（后面直接是数据）；`0xFF` 后面跟 256 字节，依次是 symbol 0..255 的频率；`1..0x7F` 后面跟 N 对 `(symbol, freq)`。symbol 256（EOF）的频率隐含为 1。
- 解码结束条件（满足任一）：遇到 EOF；输出达到上限（`0x2A + 结构大小` = 0x532）；输入读完。
- 压缩流之后是缓冲区残留，**最后 6 字节固定为 `94 45 8E D2 8A 4F`**（也是 `decrypt_save` 的成功标志）。重写时保留原文件的这段尾巴，只替换前面的压缩流。
- 常数：`TOP = 1<<24`，`BOT = 1<<16`，32 位算术；`range/total` 取整后按累计频率切分。具体实现见 `rc_decode` / `rc_encode`，与游戏写出的数据逐字节吻合。

写回流程：`decrypt → rc_decode(p, 0x2A+0x508) → 改结构体 → rc_encode(新数据, make_freq(新数据, 原频率表)) → 断言 len(流) <= 0x538-6 → 明文 = 流 + 原明文[len(流):] → 用原 seed encrypt → 用目标 HD key 签名`。

`make_freq`：原频率表能覆盖新数据里出现的所有字节就沿用，这样重新编码与游戏写出的完全一致（实测：本地 system.dat 重新编码得到 861 字节，与原明文前 861 字节逐字节相同）；覆盖不了就按字节出现次数重建一张（`max(1, min(255, count*255//max_count))`），重建的表在 xemu 实机验证可用。

> 注意：`rc_decode` 在"输入读完"时就停。游戏缓冲区里压缩流后面总有残留，所以实际文件没问题；但如果把一段刚编码出来、后面**没有任何残留**的流直接拿去解码，最后几个符号可能丢失。自己写测试时请在流后面补几个字节。

> 全新生成的 system.dat（没有任何存档）实测：byte0 = `0x3E`，即稀疏格式（62 对 symbol/freq），不是 `0xFF`；时间表全 0，顺序表 count = 0（顺序全部在"未用填充"里：0..29），总时间 21 秒，光标 0。工具对稀疏格式的底本照常解码，写出时统一用 `0xFF` 完整频率表（与 xemu 验证过的重建表一致）。所以这种文件重新编码后不会与原文件前缀逐字节相同，只有 `0xFF` 格式的底本才会。

## 4. 解码后的内容
前 0x2A 字节是固定头（以 `94 45 8E D2 8A 4F` 开头，包含 `TeamNINJA 2003`），后面是 0x508 字节的结构体：

| 结构体偏移 | 类型 | 含义 |
|---|---|---|
| +0x000 | u32 | 总游玩时间（毫秒） |
| +0x004 | u32[30] | **每档帧数**（60 帧 = 1 秒），下标 = 档位号 − 1 |
| +0x07C | u32 | 魔数 `0x20030730` |
| +0x1C6 | u8 | **顺序表的有效条目数** |
| +0x1C7 | u8[30] | **显示顺序**（0 起算的档位下标）。有效条目之后，依次填剩下的未用下标，按从小到大排 |
| +0x1E5 | u8 | 上次光标所在的档位下标 |

其余字节（解锁、设置等）的含义未研究，工具对它们原样保留，并在每次修改时断言除被改字段外全部字节不变。

### 顺序表的维护逻辑（游戏每次进存档列表都会做）
1. 先按顺序表排出现有档位；
2. 不在表里、但实际存在的档位接在最后；
3. 把结果写回顺序表。

所以：删掉一个档、进一次游戏、再把它放回来，这个档会跑到列表**最后**。要让它回到原位，需要把它按档位号插回顺序表（见下）。

## 5. save000.dat 里的帧数
save000.dat 也是同样的压缩格式：解密 → `rc_decode` → 跳过 0x2A 头 → 结构体 `+0x16628` 处的 u32 是该档帧数（解码后偏移 0x16652）。

旧代码（`ngb_save_info.py` / manager 的 `inspect`）直接读**原始明文** 0x16653，读到的是同一个值，只是因为游戏缓冲区里压缩流之后的残留恰好是未压缩的原数据（整体比解码后的偏移多 1）。本地抽查：难度、章节、存档点三个旧偏移（0x16840 / 0x16842 / 0x16849）同样等于解码后偏移减 1 处的值（抽查 8 个存档）。

新功能一律用解码后的值；旧显示逻辑保留，并加了一致性检查：manager 点选存档时会在详情里显示"解码值 / 旧读法 / 一致与否"，CLI 用 `python ngb_system_dat.py check <5443000d>`。本地 30 个存档全部一致。

## 6. 工具提供的三个操作
底本必须是用户从 xemu / 360 **当前**拷出来的 system.dat（总时间、解锁、设置要原样保留）。输出写到 `resigned/<key>_<时间>/TDATA/5443000d/system.dat`，绝不覆盖输入。每次都会：改前/改后逐档列出时间（H:MM:SS）、顺序表、count 并标出变化；断言结构体里只有目标字段变化；写出后再解码一遍并核对签名。

1. **更新单个档位**（`slot`）：从存档文件夹的 SaveMeta `Name` 取档位号，从解码后的 save000.dat 取帧数，`table[档位-1] = 帧数`。若该下标不在 `order[:count]` 里，就插在第一个比它大的下标前面，`count+1`，后面的未用下标按从小到大重新填；已经在表里则顺序表不动。
2. **按整套 UDATA 同步**（`sync`）：存在的档位写真实帧数，不存在的写 0。顺序表不动。
3. **重置顺序**（`order`）：`count = 30`，`order = 0..29`（游戏会自动跳过不存在的档位）。

```
python ngb_system_dat.py slot  <system.dat> <存档文件夹>  --key <hd_keys.json 里的名字> [--dry-run]
python ngb_system_dat.py sync  <system.dat> <...\UDATA\5443000d> --hd-key <32位十六进制>
python ngb_system_dat.py order <system.dat> --key <名字>
```

## 7. XBE 里的相关位置
| 位置 | 作用 |
|---|---|
| 0x1653E2 | 读档时取 `max(存档帧数, 表里该档的值)` |
| 0x1DB500 / 0x2E0850 | 存档时写表 |
| 0x1DA500 | 列表枚举：按存档名里的档位号放进对应格子 |
| 0x1DA300 | 顺序重建（§4 的三步） |
| 0x30FCE0 | system.dat 读取（mode 1 = `T:\system.dat`） |
| 0x310EE0 | system.dat 解码 |
| 0x1DA9E0 | 结构校验回调（要求 `+0x7C == 0x20030730`） |

## 8. 实机验证记录（xemu）
- 5 号位换成 0:00:04 的存档，只把表里第 5 格从 1,264,136 帧改成 251 帧：列表显示 000:00，读档和存档都正常。
- 删掉 5 号位后进游戏，再放回来：5 号位排到最后。
- 删掉 TDATA 后进游戏：所有档位显示 0:00，顺序恢复 1 到 30；存档或软复位后时间恢复显示。
